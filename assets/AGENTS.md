## 注意事项

- 只有用户明确要求修改时才编辑文件；只要求分析或方案时，不修改文件。
- 每组相关改动完成后创建对应的本地 Git commit。未经用户明确允许，不推送到远程仓库。
- 为代码行为变更和 Bug 修复编写或更新相关测试，只运行受影响的测试；交付前确保相关验证通过。
- 实现保持直接、清晰，不添加无依据的防御和兜底逻辑。
- 修复 Bug 后说明复现方式、错误原因、预期行为、解决办法、回归结果，并附关键修复代码。

## 项目规范

- 开始任务先读[文档地图](docs/index.md)，再按任务类型阅读相关规范、OpenSpec 文档、代码和测试。
- 目录、命名和代码归属遵循[项目规范](docs/project-conventions.md)；系统边界见[架构](docs/architecture.md)。

## 功能变更与交付

- 遵循[开发流程](docs/workflows/development.md)和[文档维护规则](docs/documentation.md)。功能规格和变更文档由 OpenSpec 管理；当前规格在 `openspec/specs/`，进行中变更在 `openspec/changes/`。不要在 `docs/` 下另建平行的 Spec 或提案。
- 功能新增、行为变化及需记录的修复按项目配置的 OpenSpec 流程生成、审阅和维护变更文档。用户已明确确认的具体要求无需重复询问；关键行为歧义先澄清，不能把尚未确认的设想当作已批准的约定。
- 修改后按[更新矩阵](docs/documentation.md#更新矩阵)同步工程文档，运行[测试指南](docs/testing.md)中受影响的测试与适用文档检查，不运行全量测试。
- 交付前核对相关 OpenSpec 文档和 diff，只提交本次代码、测试与文档，说明验证结果、文档更新和本地 commit。修复 Bug 时同时按上文说明原因和关键代码。
