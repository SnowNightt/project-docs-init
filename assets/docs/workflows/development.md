# Agent 开发流程

Spec 是单个功能长期有效的约定；变更提案记录本次准备修改的内容。已确认约定不能由 Agent 自行修改。

## 1. 阅读需求和现有约定

先读[AGENTS](../../AGENTS.md)和[文档地图](../index.md)，再看相关 Spec、架构、代码、测试和工作区未提交改动。用户只要求分析或方案时不修改文件；用户明确要求实现时可修改相关文档、代码和测试。

## 2. 记录本次功能变化

只有新增或变更功能使用[变更提案模板](../templates/proposal.md)，保存到 `docs/changes/YYYY-MM-DD-short-name/proposal.md` 并登记到文档地图。提案指出原有约定、拟议变化、原因、影响和验证方式。所有 Bug 修复都跳过提案；纯措辞修改也不建提案。

## 3. 确认约定并更新 Spec

用户已明确提出具体变化时，记录该确认依据，不重复询问。Agent 提出的行为变化或影响结果的歧义须先确认；未回复不算确认。确认后更新原功能 Spec。新增独立功能才按[Spec 模板](../templates/spec.md)创建一份新文件。现有功能缺少 Spec 时，先整理待确认约定，不把源码现状直接当作正确需求。未确认条款留在提案，正式 Spec 才标“已确认”。

## 4. 实现、测试和更新说明

按已确认 Spec 实现并更新受影响测试。计划或任务清单确有需要时放在本次变更目录。实现方法可以调整；改变功能约定须回到确认步骤。按[更新矩阵](../documentation.md#更新矩阵)同步文档，重要技术选择按[ADR 模板](../templates/adr.md)记录。

## 5. 验收并提交

按[测试指南](../testing.md)只运行相关功能测试和适用的文档检查，不运行全量测试。对照 Spec 验收标准记录实际命令、结果和人工证据；新增或变更功能写入提案或任务清单，全部通过后才把变更记录标为“已完成”。Bug 修复在交付回复中记录复现、原因、预期、解决方案和回归结果，并附关键代码。检查 diff，只提交本次代码、测试和文档，创建本地 commit，未经允许不推送。

## 状态

| 文件 | 状态 |
| --- | --- |
| 功能 Spec | 草案、已确认、已废弃 |
| 变更提案 | 草案、待确认、已确认、实现中、已完成、已取消 |

实现完成后，功能 Spec 保持“已确认”；任务进度和验收结果属于变更记录。
