# 文档维护规则

## 职责与事实来源

- README：项目用途、环境、启动和构建说明。
- AGENTS：Agent 的执行规则，只引用详细规范。
- 功能 Spec：每个功能一份长期有效的行为、限制和验收约定，放在 `docs/specs/<feature-name>.md`。旧版本由 Git 保存，Agent 不自行改变已确认条款。
- 变更记录：本次新增或变更功能的原因、条款变化、用户确认依据、实现和验证，放在 `docs/changes/YYYY-MM-DD-short-name/`。`proposal.md` 使用[模板](templates/proposal.md)；计划与任务清单按需创建。
- 架构与实现说明：描述当前代码如何工作。尚未实现的计划不得写成当前事实；实现说明引用 Spec，不重复定义业务约定。
- ADR：重要技术决定的背景、取舍和影响，使用[模板](templates/adr.md)。

实现细节以源码为准，预期行为以已确认约定为准。两者冲突时先说明差异，不把代码现状直接视为需求。

## 更新矩阵

| 改动 | 检查并同步的文档 |
| --- | --- |
| 环境要求、启动、打包命令 | README |
| 目录、命名、代码归属规则 | 项目规范 |
| 模块边界、数据流、存储和通信 | 架构；重要选择另写 ADR |
| 用户可见行为和业务规则 | 先写变更提案，经用户明确确认后更新原功能 Spec；实现后同步实现说明 |
| 测试组织、命令和验证要求 | 测试指南 |
| Agent 工作规则与文档流程 | AGENTS、开发流程、本文 |

只有新增或变更功能需要变更提案。同一功能后续变更新建变更记录，更新原 Spec，不新建另一份功能 Spec。所有 Bug 修复都不建提案；复现、原因、预期行为和验证结果写在当前对话的交付回复。若修复必须改变功能约定，该部分按功能变更处理。纯措辞修改也不建提案。

用户对具体变化的明确要求可作为确认依据，无需重复批准；笼统授权或未回复不代表同意。未确认方案留在提案，不能进入正式 Spec。功能 Spec 使用“草案、已确认、已废弃”；变更记录使用“草案、待确认、已确认、实现中、已完成、已取消”。实现完成后 Spec 仍为“已确认”。

## 文件与链接约定

- 文件名使用小写英文和连字符，新文档必须从文档地图或已登记文档可达。
- 仓库内文件使用 Markdown 相对链接；不使用本机绝对路径。路径含空格时使用尖括号。
- 草案应明确标记，不把计划或尚未实现的能力写成当前事实。
- 修改时同步相关代码、测试和文档，并在同一个本地 commit 提交；不夹带无关改动。
