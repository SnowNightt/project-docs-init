# 初始化文档契约

## 文件及事实来源

| 文件 | 初始化时写什么 | 后续如何维护 |
| --- | --- | --- |
| `AGENTS.md` | Agent 权限、工作边界、文档和交付流程；链接详细规范 | 只放执行规则，不复制长篇规范 |
| `docs/index.md` | 文档地图：按任务类型列入口，分别登记功能 Spec、变更记录、架构和模板 | 新文档必须从地图或已登记文档可达 |
| `docs/workflows/development.md` | 读约定、提案、确认、实现、验收、提交的步骤 | 与 AGENTS 和文档规则保持一致 |
| `docs/documentation.md` | README、Spec、变更记录、实现说明、ADR 的职责及更新矩阵 | 行为变化先更新约定，源码事实随实现同步 |
| `docs/testing.md` | 目标技术栈可执行的定向测试、文档检查、构建验证命令 | 命令须在项目中真实存在；尚未配置的检查标为待建 |
| `docs/project-conventions.md` | 根据实际技术选型写目录、命名、模块归属及依赖方向 | 不引入未采用的框架或假想目录 |
| `docs/architecture.md` | 进程/服务/数据边界与计划架构；已有代码时区分当前事实与目标 | 随实现更新，不把计划写成已实现 |
| `docs/templates/spec.md` | 长期功能约定模板 | 同一功能只维护一份当前 Spec |
| `docs/templates/proposal.md` | 单次新增或变更功能的提案及验证记录模板 | Bug 修复不用提案 |
| `docs/templates/adr.md` | 重要技术决策的背景、取舍和影响模板 | 仅在有重要决策时创建 ADR |

还应按实际需求生成 `docs/specs/<feature-name>.md` 和本次实现所需的 `docs/changes/YYYY-MM-DD-short-name/proposal.md`。项目 README 说明项目用途、环境和可执行命令；已有 README 应同步更新。实现说明和 ADR 只在有实际内容时新增。文件名用小写英文和连字符，仓库内链接用相对路径。

## 约定与状态

- 功能 Spec 写目标范围、编号的行为约定、限制、可长期复用的验收标准、确认依据和待确认问题。状态只用“草案、已确认、已废弃”；实现完成后仍为“已确认”。已有功能后续变化更新原 Spec，旧版本由 Git 保存。
- 已确认 Spec 的行为、限制和验收标准不得由 Agent 自行改变。用户对具体变化的明确要求可作确认依据，无需重复询问；笼统授权或未回复不等于确认。实现困难时调整技术方案，不降低约定。
- 只有新增或变更功能需要变更提案。提案记录对应 Spec、原条款、新条款、原因、用户确认依据、实现与测试计划，以及实际验收结果。状态可用“草案、待确认、已确认、实现中、已完成、已取消”。未确认的方案留在提案，不能覆盖正式 Spec。计划和任务清单按需放同一变更目录。
- 所有 Bug 修复都不建变更提案。复现、原因、预期行为、修复方法及回归结果写在交付回复；测试代码随修复提交。若修复需要改变功能约定，该部分另按功能变更处理。纯措辞修改也无需提案。

## 文档更新矩阵

| 改动 | 同步位置 |
| --- | --- |
| 环境要求、启动、打包命令 | README、测试指南（如涉及验证） |
| 目录、命名、代码归属规则 | 项目规范 |
| 模块边界、数据流、存储、通信 | 架构；重要选择另写 ADR |
| 用户可见行为和业务规则 | 变更提案、经确认后的原功能 Spec；实现后同步实现说明 |
| 测试组织、命令、验证要求 | 测试指南 |
| Agent 工作规则和文档流程 | AGENTS、开发流程、文档维护规则 |

## 验收与提交

文档建立后逐一检查链接、状态、确认依据、需求覆盖和命令真实性。代码实现后只运行受影响功能测试及项目配置的文档检查；新增或变更功能的实际测试命令、结果和人工验收证据写入提案或任务清单。全部通过后变更记录才标“已完成”。未配置的自动检查不能写成已通过。提交前核对相关 Spec 条款和 diff，代码、测试、相应文档进入同一个本地 commit，不夹带其他改动，也不推送远程。
